# E1-3 Mini NPU Simulator

코디세이 입학연수 미션 E1-3 "AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기"의 결과물입니다.

## 1. 프로젝트 개요

입력 패턴이 십자가(Cross)인지 X인지 판별하는 콘솔 프로그램입니다. 판별에는 MAC(Multiply-Accumulate) 연산을 씁니다.

- 패턴과 필터를 같은 위치끼리 곱한 뒤 모두 더해 점수를 냅니다. 점수가 큰 필터의 라벨로 판정합니다.
- 모드는 세 가지입니다.
  - 모드 1: 3×3을 직접 입력합니다.
  - 모드 2: `data.json`의 5×5, 13×13, 25×25 케이스를 한 번에 판정합니다.
  - 모드 3: 패턴 생성기입니다(보너스).
- 크기별 MAC 연산 시간을 재서, 연산 횟수 N²에 비례한다는 것(O(N²))을 수치로 확인합니다.
- Python 3.8 이상의 표준 라이브러리(`json`, `time`, `re`, `dataclasses`, `unittest` 등)만 씁니다. NumPy 같은 외부 라이브러리는 쓰지 않습니다.

## 5. 구현 요약

### 5.1 데이터 구조: `Matrix`

- 값은 리스트의 리스트(`self._rows`)에 담습니다. `get(r, c)`와 `set(r, c, value)`로 특정 위치를 읽고 씁니다.
- 크기는 1 이상의 정수면 됩니다. 3×3, 5×5, 13×13, 25×25를 모두 같은 클래스로 처리합니다(테스트 `test_supported_sizes`).
- `Matrix.from_rows()`는 저장하기 전에 세 가지를 검증합니다.
  - 정사각형인지(모든 행의 길이 = 행 수)
  - 값이 숫자인지(`bool`과 문자열은 거부)
  - 유한한 수인지(`NaN`, `inf`는 거부)
- 값은 모두 `float`로 저장합니다. 정수 필터(0/1)와 실수 필터(0.1, 7.5)를 같은 방식으로 더하기 위해서입니다.
- 함정 하나를 피했습니다. `[[0.0] * n] * n`으로 만들면 모든 행이 같은 리스트를 가리킵니다. 그러면 한 칸을 바꿀 때 열 전체가 바뀝니다. 그래서 행마다 새 리스트를 만듭니다(테스트 `test_rows_are_independent`).
- **대안 비교:** 그냥 리스트의 리스트를 쓰면 코드는 짧습니다. 하지만 정사각형 검증과 값 검증이 여러 곳에 흩어집니다. 클래스로 감싸면 "잘못된 행렬은 아예 만들어지지 않는다"는 규칙을 한 곳에서 지킬 수 있습니다.

### 5.2 MAC 연산

```python
def mac_2d(pattern_rows, filter_rows):
    total = 0.0
    for r in range(n):
        p_row = pattern_rows[r]; f_row = filter_rows[r]
        for c in range(n):
            total += p_row[c] * f_row[c]
    return total
```

- 반복문으로 직접 곱하고 더합니다. `sum()`, `zip()`, NumPy는 쓰지 않습니다.
- 곱셈은 N²번, 덧셈은 N²번입니다.
- `mac(pattern, filter)`는 두 Matrix의 크기가 다르면 계산 전에 `ValueError`를 냅니다. 크기가 다른 두 배열을 곱하면 일부 칸만 계산되거나 `IndexError`가 납니다. 그 전에 막는 것입니다.

### 5.3 라벨 정규화

data.json에는 같은 뜻의 라벨이 여러 모양으로 들어 있습니다.

| 원본 위치 | 원본 값 | 표준 라벨 |
|---|---|---|
| `expected` | `'+'` | `Cross` |
| `expected` | `'x'` | `X` |
| 필터 키 | `'cross'` | `Cross` |
| 필터 키 | `'x'` | `X` |

- `normalize_label()`은 앞뒤 공백을 지우고 소문자로 바꾼 뒤 별칭 표에서 찾습니다. 표에 없으면 `None`을 돌려줍니다.
- 필터 키와 `expected`가 **같은 함수**를 거쳐 표준 라벨이 됩니다. 판정 결과(`Cross`/`X`)와 `expected`의 비교, 콘솔 출력은 모두 이 표준 라벨로 합니다.
- **왜 필요한가:** 정규화 없이 `'+' == 'Cross'`나 `'x' == 'X'`로 비교하면 판정이 맞아도 문자열이 달라 FAIL이 됩니다. 이것은 로직 문제가 아니라 라벨 규칙(스키마) 문제입니다. 입구에서 한 번 표준화하면 이후 코드는 라벨이 두 가지뿐이라고 가정할 수 있습니다.
- **해석 못 한 라벨:** 예를 들어 `'o'`는 추측하지 않습니다. 그 케이스만 "라벨 오류"로 FAIL 처리합니다. 모르는 값을 아무 라벨에나 끼워 맞추면 틀린 PASS가 생길 수 있기 때문입니다.

### 5.4 점수 비교 정책 (epsilon)

```python
EPSILON = 1e-9
def decide(score_a, score_b, epsilon=EPSILON):
    if abs(score_a - score_b) < epsilon:
        return None           # 동점 → UNDECIDED / 판정 불가
    return "A" if score_a > score_b else "B"
```

- **왜 `==`나 `>`만으로 비교하지 않는가:** 0.1은 2진수로 정확히 나타낼 수 없습니다. 그래서 더하는 순서에 따라 결과가 조금씩 달라집니다.
  - 예: `0.1 + 0.2 == 0.3`은 `False`입니다.
  - 예: 0.1을 9번 더하면 `0.8999999999999999`가 됩니다.
  - 수학적으로는 같은 두 점수도 끝자리 하나 차이로 "한쪽이 크다"고 판정될 수 있습니다.
- **1e-9를 고른 이유:**
  - 이번 데이터의 점수는 0.1~53 범위입니다. 이 범위에서 누적 오차는 1e-15 수준입니다(실측: 1.1e-16 ~ 2.7e-15).
  - 반대로 진짜 차이가 나는 경우는 최소 0.1 단위입니다.
  - 1e-9는 이 둘 사이에 넉넉히 들어갑니다. 오차는 동점으로 묶고, 진짜 차이는 놓치지 않습니다.
- **동점일 때:**
  - 모드 1은 `판정 불가 (|A-B| < 1e-9)`를 출력합니다.
  - 모드 2는 `UNDECIDED`로 판정합니다. 표준 라벨이 아니라 `expected`와 같을 수 없으므로 FAIL로 셉니다.
  - 동점일 때 아무 쪽이나 고르면, 맞아도 우연입니다.
- **한계:** 절대 오차 기준이라 점수 규모가 아주 커지면 맞지 않습니다. 예를 들어 1e9 규모에서는 누적 오차 자체가 1e-9를 넘을 수 있습니다. 그런 데이터라면 상대 오차(`math.isclose(a, b, rel_tol=1e-9, abs_tol=1e-9)`)로 바꾸는 것이 맞습니다. 이번 데이터 범위에서는 두 방식의 결과가 같아서, 미션 권장 기준인 절대 오차를 유지했습니다.

**모드 2 (data.json)**

한 케이스가 잘못돼도 프로그램은 멈추지 않고, 그 케이스만 FAIL 처리합니다.

| 상황 | 처리 단위 | 메시지 예 |
|---|---|---|
| 파일 없음 / JSON 문법 오류 / `filters`·`patterns` 없음 | 파일 전체 | `✗ data.json을 읽을 수 없습니다: JSON 문법 오류: ... (3행 5열)` 후 메뉴 복귀 |

| 패턴 키가 `size_{N}_{idx}` 형식이 아님 | 그 케이스 FAIL | `키 형식 오류: size_{N}_{idx} 형태가 아님` |
| `expected` 없음 / 해석 불가 | 그 케이스 FAIL | `라벨 오류: expected 'o'를 Cross/X로 해석할 수 없음` |
| 해당 크기 필터가 로드되지 않음 | 그 케이스 FAIL | `필터 없음: size_13 필터가 로드되지 않음` |
| `input` 없음, 정사각형 아님, 숫자 아님 | 그 케이스 FAIL | `입력 형식 오류: 정사각형이 아닙니다: ...` |
| 키의 N과 패턴 크기가 다름 | 그 케이스 FAIL | `크기 불일치: 키 N=5인데 패턴은 13×13 (size_5 필터와 계산 불가)` |
| 점수 동점 | 그 케이스 FAIL | `동점(UNDECIDED) 처리 규칙에 따라 FAIL` |
| 판정 ≠ expected | 그 케이스 FAIL | `판정 X ≠ expected Cross` |

위 실패 상황은 모두 `tests/test_npu.py`의 `DataLoaderTest`에서 의도적 오류 입력으로 확인합니다.

## 7. data.json 스키마

```json
{
  "meta": { "version": "1.0", "type": "json" },
  "filters": {
    "size_5":  { "cross": [[...5개...], ...5행], "x": [[...]] },
    "size_13": { "cross": ..., "x": ... },
    "size_25": { "cross": ..., "x": ... }
  },
  "patterns": {
    "size_5_1": { "input": [[...]], "expected": "x" },
    "size_5_2": { "input": [[...]], "expected": "+" }
  }
}
```

- **키 규칙:** 패턴 키 `size_{N}_{idx}`에서 정규식 `^size_(\d+)_(\d+)$`로 N을 꺼냅니다. 그 N으로 필터 `size_N`을 고릅니다.
  - 키에서 크기를 읽는 이유는 필터를 고르기 위해서입니다. 다만 키를 그대로 믿지 않고, 실제 `input` 크기와 다시 맞춰 봅니다.
  - 키와 실제 크기가 다르면 데이터 작성 실수입니다. 계산하지 않고 FAIL로 남깁니다.
- **라벨 규칙:** 필터 쪽은 `cross`/`x`, 정답 쪽은 `+`/`x`로 같은 뜻을 다르게 적습니다. 그래서 5.3의 정규화가 필요합니다.
- `meta`는 판정에 쓰지 않으므로 읽기만 하고 검증하지 않습니다.
- 실제 데이터의 필터 값은 0/1만이 아닙니다. 가중치가 들어 있습니다. 예: size_5 Cross 필터의 가운데 칸은 0.9, X 필터는 0.1, size_13 X 필터의 가운데 칸은 7.5. 이 가중치가 아래 동점의 원인입니다.

### 8.2 실패 원인 분석

실패 3건의 원인을 "데이터/스키마 문제", "로직 문제", "수치 비교 문제" 순서로 하나씩 배제했습니다.

**① 데이터/스키마 문제인가? → 아니다.**
- 필터 3종이 모두 로드됐습니다. 패턴 6건 모두 키의 N과 `input` 크기, 필터 크기가 일치합니다.
- `expected`의 `'x'`, `'+'`는 모두 표준 라벨로 정규화됐습니다.
- 라벨 정규화를 빼면 `'x' ≠ 'X'`, `'+' ≠ 'Cross'`라서 6건이 모두 FAIL이 됩니다. 실제로 PASS 3건이 나온 것은 정규화가 동작한다는 증거입니다.

**② 로직(MAC·판정) 문제인가? → 아니다.**
- 같은 프로그램이 size_5_2, size_13_1, size_25_2는 맞혔습니다.
- 실패 3건의 점수를 `Decimal`(10진수 정확 계산)로 다시 계산했습니다.

| 케이스 | Cross 점수 (정확값) | X 점수 (정확값) | float 차이 | `>`만 쓸 때 판정 | expected |
|---|---|---|---|---|---|
| size_5_1 | 0.90 | 0.90 | 1.1e-16 | Cross | X |
| size_13_2 | 7.50 | 7.50 | 2.7e-15 | X | Cross |
| size_25_1 | 4.90 | 4.90 | 1.8e-15 | Cross | X |

- 정확히 계산해도 두 점수가 **같습니다**. MAC이 틀린 값을 낸 것이 아닙니다. 이 필터 가중치로는 원래 동점인 입력입니다.
- 동점이 생기는 구조는 이렇습니다.
  - size_5_1의 입력은 X 모양(1이 9칸)입니다.
  - X 필터와는 9칸이 겹치지만 가중치가 0.1이라 0.1×9 = 0.9입니다.
  - Cross 필터와는 가운데 1칸만 겹치지만 그 칸의 가중치가 0.9라 0.9입니다.
  - size_13_2(0.3×25 = 7.5 대 가운데 7.5)와 size_25_1(0.1×49 = 4.9 대 가운데 4.9)도 같은 구조입니다.

**③ 수치 비교 문제다. → epsilon 정책으로 "틀린 판정"을 "판정 불가"로 바꿨다.**
- float 끝자리 차이(1e-16~1e-15)는 0.1을 여러 번 더하는 누적 오차입니다.
- epsilon 없이 `>`로만 비교하면 3건 모두 **expected와 반대 라벨**을 고릅니다(표의 "`>`만 쓸 때 판정" 열, 테스트 `test_plain_comparison_would_mislabel`). 오차의 방향이 우연히 틀린 쪽으로 기운 것입니다. 이 경우 "점수 계산은 맞는데 판정이 틀린" FAIL이 되고, 원인을 찾기도 어렵습니다.
- epsilon 정책을 쓰면 세 건은 "모른다(UNDECIDED)"로 정직하게 보고됩니다. 실패 사유도 "동점 규칙"으로 분명해집니다.
- 참고로 같은 값을 Python 3.12의 `sum()`으로 더하면 `0.9`와 `0.9`로 정확히 같게 나옵니다. `sum()`은 보정 합산을 하기 때문입니다. 즉 "얼마나 차이 나는가"는 더하는 방법에 따라 달라집니다. 그래서 비교는 차이의 크기와 상관없이 허용오차로 해야 합니다.

**개선 방향 (구현하지 않고 분석만 함)**
- 미션 규칙은 "MAC 점수 비교, 동점이면 UNDECIDED"이므로 실패 3건은 규칙대로 FAIL로 남겼습니다.
- 동점을 줄이려면 점수 정의를 바꿔야 합니다. 예를 들어 점수를 필터 가중치 합으로 나누는 **정규화 점수**(MAC ÷ 필터 합)를 쓰면 세 건 모두 expected와 같아집니다.

| 케이스 | Cross 정규화 점수 | X 정규화 점수 | 판정 |
|---|---|---|---|
| size_5_1 | 0.9 ÷ 8.9 = 0.101 | 0.9 ÷ 0.9 = 1.000 | X (= expected) |
| size_13_2 | 7.5 ÷ 7.5 = 1.000 | 7.5 ÷ 14.7 = 0.510 | Cross (= expected) |
| size_25_1 | 4.9 ÷ 52.9 = 0.093 | 4.9 ÷ 4.9 = 1.000 | X (= expected) |

- 다만 이렇게 하면 미션이 정한 판정 기준 자체를 바꾸게 됩니다. 그래서 제출 코드에는 넣지 않고 분석으로만 남깁니다.

### 8.3 성능 분석과 시간 복잡도

**모드 2 성능 표 (각 크기 10회 평균, 측정 예)**

```
크기       평균(ms) 2D   평균(ms) 1D  연산 횟수(N²)  2D ns/연산
---------------------------------------------------------------
3×3             0.0005        0.0003              9        56.7
5×5             0.0009        0.0006             25        36.0
13×13           0.0041        0.0047            169        24.5
25×25           0.0135        0.0135            625        21.6
```

**측정 방법**
- `time.perf_counter()`로 `mac_2d()` 호출 한 번씩을 따로 잽니다. 10회 평균을 ms로 냅니다.
- 입력, 출력, 파일 읽기는 측정 구간 밖에서 끝냅니다. 행렬을 펼치는 시간도 1D 측정에 넣지 않습니다.
- 첫 호출은 준비 비용이 섞이므로 한 번 미리 돌리고 버립니다(warm-up).
- 입력은 생성기로 만든 X 패턴입니다. 크기가 같으면 항상 같은 입력입니다. 필터는 data.json의 Cross 필터를 쓰고, 3×3은 생성기 필터를 씁니다.

**O(N²) 근거**
1. **코드 근거:** `mac_2d`는 바깥 반복 N번 × 안쪽 반복 N번 = 곱셈·덧셈 N²번입니다. 다른 연산은 없습니다. 입력 크기가 N×N이므로 칸 수에 정비례(선형)하고, 한 변의 길이 N에 대해서는 O(N²)입니다.
2. **측정 근거:** 5×5 → 25×25에서 N은 5배, N²은 25배(25 → 625)입니다. 측정 시간은 0.0009 → 0.0135 ms로 약 15배입니다.
   - 25배보다 작은 이유는 크기와 관계없는 고정 비용(함수 호출, 반복문 준비) 때문입니다. 작은 크기일수록 이 비용의 비중이 큽니다.
   - "연산 하나당 시간(ns/연산)"을 보면 56.7 → 36.0 → 24.5 → 21.6 ns로 줄다가 약 20 ns에서 일정해집니다.
   - 시간 ÷ N²가 상수에 수렴한다는 것이 곧 시간 ∝ N²라는 뜻입니다.
3. **더 큰 크기로 확인 (`--repeat 1000` 수준의 1000회 평균):**

| 크기 | N² | 평균(ms) | ns/연산 |
|---|---|---|---|
| 25×25 | 625 | 0.0136 | 21.7 |
| 51×51 | 2,601 | 0.0536 | 20.6 |
| 101×101 | 10,201 | 0.2032 | 19.9 |

   - 25 → 101에서 N²은 16.3배, 시간은 14.9배입니다. 연산당 시간은 거의 같습니다.
   - 따라서 필터 한 변이 2배가 되면 시간은 약 4배가 됩니다.
   - 미션 소개처럼 수백×수백 필터를 수천 개 쓰면 이 N²이 곱으로 쌓입니다. 이것이 NPU처럼 MAC을 병렬로 처리하는 하드웨어가 필요한 이유입니다.

**측정의 한계**
- 3×3 한 번의 계산은 1 µs도 걸리지 않습니다. 그래서 10회 평균은 실행할 때마다 ±30% 정도 흔들립니다. 표의 숫자는 실행마다 조금씩 다릅니다.
- 추세(시간 ∝ N²)를 보려면 `--repeat 1000`으로 반복을 늘리는 편이 안정적입니다.
- 측정값은 CPython 3.12, Windows 11 노트북 기준입니다.

### 8.4 보너스: 1차원 배열 최적화 비교

- `mac_flat`은 행렬을 길이 N²의 1차원 리스트로 펼쳐 반복문 하나로 계산합니다. 결과는 2D와 항상 같습니다(테스트 `test_flat_equals_2d`).
- 동일 입력, 동일 반복 횟수 조건의 결과는 다음과 같습니다.
  - 작은 크기(3×3, 5×5)에서는 1D가 약 30% 빠릅니다. 바깥 반복문과 행 꺼내기 비용이 없어지기 때문입니다.
  - 13×13 이상에서는 차이가 없거나 2D가 조금 더 빠릅니다(101×101: 2D 0.203 ms, 1D 0.251 ms).
- **해석:** C 언어라면 1차원 배열은 메모리에 연속으로 놓여 캐시 효율이 좋아집니다. 하지만 Python 리스트는 float 객체를 가리키는 주소의 목록입니다. 1D로 펼쳐도 실제 값은 연속 메모리가 아닙니다.
  - 그래서 Python에서는 메모리 배치보다 인터프리터가 명령 하나를 처리하는 비용이 시간을 좌우합니다.
  - 2D 구현은 행을 한 번만 꺼내(`p_row = pattern_rows[r]`) 안쪽 반복에서 인덱스를 한 번만 씁니다. 그래서 이미 1D와 같은 수의 인덱스 접근을 합니다.
  - 결론: Python에서 1D 변환의 이득은 작은 크기의 고정 비용 절감 정도입니다. 접근 패턴 단순화의 효과를 제대로 보려면 연속 메모리를 쓰는 언어나 하드웨어(NPU)가 필요합니다.

## 9. 과제 목표별 설명

| 목표 | 설명 | 근거 위치 |
|---|---|---|
| MAC이 무엇이고 AI에서 왜 중요한가 | 같은 위치끼리 곱해서(Multiply) 누적해 더하는(Accumulate) 연산입니다. 신경망의 합성곱·완전연결층은 결국 "입력 × 가중치의 합"이라 MAC의 반복입니다. 연산 하나는 단순하지만 수억 번 반복되므로, 이를 병렬로 처리하는 NPU가 생겼습니다. | 5.2, 8.3 |
| 곱하고 더해서 유사도를 내는 원리 | 필터가 1(또는 큰 가중치)인 칸에 입력도 값이 있으면 점수가 올라갑니다. 즉 겹치는 칸이 많을수록, 가중치가 클수록 점수가 큽니다. Cross 패턴은 Cross 필터와 2N-1칸, X 필터와 가운데 1칸이 겹칩니다(테스트 `test_scores_grow_with_n`). | 8.5 |
| 키·라벨 규칙 해석과 정규화 이유 | 키에서 N을 꺼내 필터를 고르고, 실제 크기와 다시 대조합니다. 라벨은 `+`/`cross` → Cross, `x` → X로 입구에서 통일합니다. 그래야 비교 로직이 표기 차이에 흔들리지 않습니다. | 5.3, 7 |
| 부동소수점 오차와 epsilon | 실제 데이터에서 동점 3건이 1e-16~1e-15 차이로 갈렸습니다. `>`만 쓰면 3건 모두 반대 라벨을 고릅니다. epsilon으로 동점을 판정 불가로 처리합니다. | 5.4, 8.2 |
| 크기별 시간 측정과 O(N²) | 크기별 10회 평균을 측정했습니다. 연산당 시간이 약 20 ns로 일정해지는 것으로 시간 ∝ N²를 보였습니다. | 8.3 |
| 실패 원인을 3분류로 진단 | 데이터/스키마 → 로직 → 수치 비교 순서로 배제했습니다. 정확 계산(Decimal)으로 "진짜 동점"임을 확인했습니다. | 8.2 |

## 12. 한계와 다음 단계

- **판정 기준:** 미션 규칙대로 MAC 원점수만 비교합니다. 그래서 가중치 설계상 동점인 입력은 판정하지 못합니다. 정규화 점수 같은 대안은 8.2에 분석만 해 두었습니다.
- **epsilon:** 절대 오차라서 점수 규모가 아주 크면 상대 오차로 바꿔야 합니다(5.4).
- **필터 수:** 두 가지(Cross, X)만 다룹니다. 라벨이 늘어나면 `decide()`를 "가장 큰 점수, 1·2위 차이가 ε보다 작으면 판정 불가"로 일반화해야 합니다.
- **생성기:** 가운데 칸이 필요해서 홀수 N만 지원합니다.
- **측정 정밀도:** 아주 작은 크기는 타이머 해상도와 OS 스케줄링의 영향을 받습니다(8.3).
